## `createTool(config)`

```typescript
import { createTool } from "@cline/sdk"
```

Creates a typed tool. Also re-exported from `@cline/agents` and `@cline/core`.

```typescript
const tool = createTool({
  name: "get_current_time",
  description: "Return the current time as ISO string.",
  inputSchema: { type: "object", properties: {} },
  execute: async (_input, context) => {
    return { now: new Date().toISOString() }
  },
})
```

`inputSchema` can be either JSON Schema or a Zod schema. Zod schemas are also
used for runtime input validation. Raw JSON Schema tools can provide
`validateInput(input)` to return validated or transformed input, or throw to
return a model-visible tool error.

## AgentTool

```typescript
interface AgentTool<TInput = unknown, TOutput = unknown> {
  name: string
  description: string
  inputSchema: Record<string, unknown>
  concurrency?: "safe" | "exclusive"
  validateInput?: (input: unknown) => unknown
  execute: (input: TInput, context: AgentToolContext) => Promise<TOutput> | TOutput
  timeoutMs?: number
  retryable?: boolean
  maxRetries?: number
}
```

Defaults from `createTool`:

| Field | Default |
|-------|---------|
| `concurrency` | `"exclusive"` |
| `timeoutMs` | `30000` |
| `retryable` | `false` |
| `maxRetries` | `0` |

`concurrency` is a property of the tool, not of one call's arguments. Declare
`"safe"` only for a tool that reads and holds no shared state; everything else
runs alone. The runtime batches the safe tools of a turn behind a bounded worker
pool and restores the original result order, so batching changes latency, not
semantics. Set `maxParallelToolCalls` to `1` to serialise everything.

Each execution attempt receives a tool-scoped abort signal and is bounded by
`timeoutMs`. A timeout becomes a structured tool error so the model can recover.
Retries occur only when `retryable` is explicitly `true`; they use bounded
exponential backoff controlled by the runtime's `toolRetryDelayMs` setting.
Retries should therefore be enabled only for idempotent or effectively
idempotent operations.

Parallel batches use a bounded worker pool and wait for every call to settle
before continuing. A successful `lifecycle.completesRun` tool completes the run
after the rest of its batch has settled, so every emitted tool call retains a
matching tool result.

## AgentToolContext

```typescript
interface AgentToolContext {
  sessionId?: string
  agentId: string
  conversationId?: string
  runId?: string
  iteration: number
  toolCallId?: string
  toolCallIndex?: number
  signal?: AbortSignal
  globPath?: string
  metadata?: Record<string, unknown>
  snapshot?: AgentRuntimeStateSnapshot
  emitUpdate?: (update: unknown) => void
}
```

`globPath` carries a workspace-relative subdirectory that scopes name-pattern
lookups for the duration of one call, so a single executor can serve every
pattern of a batched lookup. Values that resolve outside the workspace root are
rejected by the executor rather than clamped.

## ToolPolicy

```typescript
interface ToolPolicy {
  enabled?: boolean
  autoApprove?: boolean
}
```

Tool names not listed in a policy map default to enabled and auto-approved.

## Tool Approval

When `autoApprove` is `false`, the runtime sends a `ToolApprovalRequest` through
its host callback. The request includes the durable `runId`,
`toolCallIndex`, and `assistantMessageId`, and its optional `signal` is
cancelled when the run aborts. Local and hub hosts persist the request and
decision through `DurableToolApprovalCoordinator`; a client response is
accepted only for the assigned approval principal. Pending requests are
replayed when the client attaches to the session.
