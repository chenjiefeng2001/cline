Cline's VS Code settings live in the settings dialog (**Agent**, **Files**,
**Memory** and **Web Search** sections) and in `settings.json` under the `cline.`
prefix. Every setting listed here is editable in the UI and reaches the runtime —
there are no declared-but-unwired settings.

## Run guardrails

These bound what a single agent run may cost.

| Setting | Default | Meaning |
|---------|---------|---------|
| `cline.maxIterations` | `0` | Model round-trips per turn. **`0` means no limit.** Reaching a limit ends the turn as `max_iterations`; it does not crash |
| `cline.runBudgetMaxTotalCost` | `5` | Spend ceiling in USD for one run. **`0` means no ceiling.** Reaching it ends the turn as `budget_exhausted` |
| `cline.maxConsecutiveMistakes` | `3` | Consecutive mistakes before the run pauses for you (0–10) |
| `cline.maxToolCalls` | `0` | Tool calls per run. **`0` means no limit.** Reaching it ends the run as `tool_calls_exhausted` |
| `cline.maxSubAgentDepth` | `0` | Levels of `spawn_agent` delegation. **`0` means "unset", so the SDK default of 1 applies** — see below |
| `cline.lazyToolLoading` | `false` | Hide rarely-used tool schemas behind a `tool_search` meta-tool — see below |

`0` is a decision, not a typo: it removes the ceiling entirely, which is useful
for long autonomous runs. A value that is not a usable number — negative,
non-finite, blank — falls back to the default, because a mistyped setting must
never silently remove a guardrail.

`maxToolCalls` bounds an axis `maxIterations` does not. One turn can issue many
tool calls while still counting as a single iteration, and the repeated-identical-
result detector stays silent when the model varies its calls, so without a ceiling
of its own a run can spend real money with nothing to stop it. It is off by
default because an unexpected cap truncates legitimate work; set it where a runaway
agent costs money rather than where it merely wastes tokens. Tool calls refused by
the cap each return an explicit error result, so the transcript stays consistent.

`maxSubAgentDepth` counts nesting levels with the root session as `0`. The effective
default of `1` means the root session can delegate but a delegate cannot delegate
again; the `spawn_agent` tool is withheld at the limit rather than erroring, so a
delegate does not spend a turn on a call that cannot succeed. Raise it only for
genuinely recursive delegation — every extra level opens another context, spends
its own tokens and runs its own tools.

The CLI applies the same ceilings with the same effective behaviour (50 round-trips
and $5, overridable by flag), so a task behaves the same in either host.

## Parallel tool calls

| Setting | Default | Meaning |
|---------|---------|---------|
| `cline.maxParallelToolCalls` | `6` | Tool calls that may run concurrently in one turn. `1` forces fully serial execution |

Only tools that declare themselves concurrency-safe batch together. Today that
is `read_files`, `search_codebase` and `glob`; everything else runs on its own,
and batching never changes the order results are returned in.

## Files and workspace

| Setting | Default | Meaning |
|---------|---------|---------|
| `cline.fileBoundaryEnabled` | `true` | Confine `read_files` and `editor` to the session workspace |
| `cline.fileBoundaryAdditionalRoots` | `""` | Extra directories the file tools may touch. Accepts a JSON array or a newline/comma separated list |

With the boundary on, the file tools cannot touch paths outside the workspace.
Widening it is done by adding roots rather than by switching the guard off.

## Shell sandbox

Separate from the file boundary above, which checks paths inside the file tools.
This confines the **process**, so it also covers whatever a command spawns — a
`curl` inside a script, a subprocess, a tool the agent did not know about.

| Setting | Default | Meaning |
|---------|---------|---------|
| `cline.sandboxEnabled` | `false` | Run shell commands inside an OS process sandbox: writes confined to the workspace, network denied |
| `cline.sandboxNetworkAccess` | `false` | Let sandboxed commands reach the network. Also removes loopback access for them |
| `cline.sandboxBackend` | `""` | Force a backend (`seatbelt`, `bubblewrap`). Empty means the platform default |

macOS uses Seatbelt (`sandbox-exec`) and Linux uses bubblewrap. **There is no
Windows backend.**

Two things to know before turning it on:

- **It is fail-closed.** Where no backend is available — Windows, or a machine
  without `bwrap` installed — shell commands **fail** rather than running
  unsandboxed. That is deliberate: a sandbox that silently does nothing is worse
  than one that is visibly absent. The session factory logs the reason when it
  cannot honour the request.
- **Network is denied by default.** The sandbox draws a filesystem-write boundary;
  leaving egress open would hand every sandboxed `curl` a working socket, which is
  not an isolation boundary. Both mainstream alternatives gate the network at this
  layer too.

The same switch is available in the CLI as `--sandbox` / `--sandbox-network`, and
in ACP sessions as a session config option (an editor client can set it, seeded by
`CLINE_PROCESS_SANDBOX`).

## Lazy tool loading

Every model request carries the full schema of every tool the session registered.
Teams alone contribute 18, so a session that never uses teams still pays for all
18 on every turn.

With `cline.lazyToolLoading` on, rarely-used tool schemas are hidden behind a
`tool_search` meta-tool. Deferred tools stay registered and callable — the model
searches for one, and the best matches become visible to it on the next turn.
`team_*` tools are deferred by default.

It defaults to **off**, because revealing a tool costs one search round trip. On a
default session it removes about 39% of the per-request tool array, at a cost of
roughly 520 tokens for `tool_search` and its catalogue — so it suits long sessions
that mostly avoid teams, and suits team-heavy sessions poorly. The same switch is
available in the CLI as `--lazy-tool-loading`.

## MCP

**Use MCP servers** in the auto-approve settings gates both MCP tool calls and the
resource and prompt tools, so turning it off stops all three.
