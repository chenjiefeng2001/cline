Cline tools are executable functions the model can call while working. The model decides which tool to call, Cline runs it, then returns results back to the model.

## Built-In Tools (ClineCore)

When running through `ClineCore`, these built-ins are available:

| Tool | Description |
|------|-------------|
| `read_files` | Batch read files, with optional inclusive line ranges for long files |
| `search_codebase` | Regex search across the workspace; several queries per call |
| `glob` | Find files by name pattern, e.g. `**/*.test.ts` |
| `run_commands` | Execute shell commands |
| `editor` | Create, replace and insert text in files |
| `apply_patch` | Apply unified diffs (routed in place of `editor` for some models) |
| `fetch_web_content` | Fetch a URL and extract content with a prompt |
| `skills` | Run a configured skill inside the main conversation |
| `ask_question` | Ask the user one multiple-choice question |
| `submit_and_exit` | Submit a final answer and stop (opt-in, off by default) |

Hosts may add their own. The VS Code extension contributes `attempt_completion`,
and any tool an MCP server publishes is registered alongside the built-ins.

<Note>
  `Agent` from `@cline/agents` does not include built-ins by default. You provide tools explicitly.
</Note>

## Tool Categories

- **Reading and finding files**: `read_files`, `search_codebase`, `glob`
- **Editing**: `editor`, `apply_patch`
- **Execution**: `run_commands`
- **External retrieval**: `fetch_web_content`
- **Capabilities and dialogue**: `skills`, `ask_question`, `submit_and_exit`

## Concurrency

Every tool declares whether it may run alongside others:

| Value | Meaning |
|-------|---------|
| `exclusive` | Runs alone. The default, so a new tool is safe unless it opts in. |
| `safe` | Read-only with no shared state, so the runtime batches these together behind a worker pool while preserving result order. |

`read_files`, `search_codebase` and `glob` are `safe`; everything else runs alone.
Set `maxParallelToolCalls` to `1` for fully serial execution.

## Approval and Policy Controls

Cline can run tools with approval or auto-approval, depending on settings/policies. Typical patterns:

- Require approval for risky tools (for example `run_commands`, write/edit operations)
- Auto-approve low-risk tools (for example read/search operations)
- Disable specific tools entirely when needed

Reads follow the read-files approval toggle, and the MCP catalogue tools follow the
MCP toggle, so switching either off also stops the tools that belong to it.

For policy examples, see [SDK Tools](/sdk/tools) and [Permission Handling](/sdk/guides/permission-handling).

## MCP Tools

Cline can also call tools discovered from MCP servers configured in `.cline/mcp.json`.

MCP tools are loaded alongside built-ins, so Cline can use both local tools and external integrations in one task.

### MCP Resources and Prompts

The VS Code extension additionally exposes two parts of the MCP surface that are
not tools:

| Tool | Description |
|------|-------------|
| `list_mcp_resources` | List the resources and resource templates a server publishes |
| `read_mcp_resource` | Read one resource by server and URI; large bodies are truncated |
| `list_mcp_prompts` | List a server's prompts and their arguments |

<Warning>
  These three are provided by the VS Code extension's MCP integration. The SDK's own
  MCP layer still speaks tools only, so the CLI, hub and desktop app do not have them
  even when the same server is connected.
</Warning>

Prompt *execution* is not exposed anywhere: `prompts/get` returns a message list,
and injecting that into a conversation is a different operation from a tool call.

See [MCP Overview](/mcp/mcp-overview) and [SDK Tools → MCP Tools](/sdk/tools#mcp-tools).

## Custom Tools

<Warning>
  This feature currently only applies to Cline SDK, CLI, and Kanban. This feature is not applicable on VSCode and JetBrains Extension for now.
</Warning>

Beyond built-ins and MCP, you can create custom tools and add them through plugins.

- Define tool behavior and input schema in plugin code
- Register tools during plugin setup
- Expose those tools to agents alongside built-ins

See:
- [SDK Plugins](/sdk/plugins)
- [Writing Plugins (examples)](/sdk/guides/writing-plugins)
- [SDK Tools: Creating Custom Tools](/sdk/tools#creating-custom-tools)

## Legacy Tool Names vs Current Runtime Tools

Some older docs and examples reference names like `read_file`, `replace_in_file`,
`search`, `fetch_web` or `bash`. The runtime uses the built-in names listed above:
`read_files`, `editor`, `search_codebase`, `fetch_web_content` and `run_commands`.

<Warning>
  A tool name that does not exist fails silently in some paths: an unknown name in a
  policy map is treated as auto-approved, and a UI that does not know a name may
  render nothing at all. If you are following an older guide, check the name against
  the table above.
</Warning>
